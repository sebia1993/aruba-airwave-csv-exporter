# 실제 워커 격리·장시간 반복 안정성 검증 (기능 동결)

- 작성일: 2026-10-29
- 기준: main commit fc46a6e11f3369e9c341010b29fb48b0b3751a0a
- 요청: 3~5개 실제 독립 프로세스 모의 통합 테스트 + Windows 장시간 반복 안정성 테스트
- 승인: 이전 대화에서 사용자 기능 추가/수정/삭제 금지 확정; 이번 "진행해"는 위 두 안정화 검증 실행 승인
- 실제 AirWave 서버 검증: 사용자가 직접 수행, CI에서는 접속하지 않음

## 외부 동작 불변

서버 최대 5대, 기본 동시 3대, FIFO, 180초 재시도, 15~30초 기다림, 기존 예약 작업·CLI·GUI·CSV 파일명·인코딩·열 구조·계정 보관 및 정상 백업 방식은 모두 유지한다.

## 기존 검증의 간극

현행 `tests/test_multi_airwave_e2e.py`는 3개의 스레드에서 브라우저 로컬 HTML 테스트를 실행하지만, 실제 애플리케이션의 `WorkerLauncher`, Windows Job Object, `run_batch` 병렬 프로세스 및 5대 FIFO 작업 경로를 검증하지 않는다. 기존 프로세스 테스트는 단일 워커 종료에 집중한다.

## 선택한 접근법

A. 실제 회사 AirWave 3대를 CI에서 호출 → 회사 연결·계정·비밀정보가 필요해 제외.
B. 운영 코드를 수정해 테스트 전용 로그인·CSV 우회 모드를 심기 → 사용자 기능 동결에 어긋날 위험으로 제외.
C. **테스트 전용 별도 모의 워커**로 기존 `WorkerLauncher`·`run_batch`를 실제 운영체제 프로세스로 실행하고, 빌드된 Windows EXE는 정상적으로 실패하는 실제 `--worker` 경로를 별도 검증 → 채택.

테스트 전용 워커는 자체 CSV 가상 데이터를 만들고, 제품 코드가 원래 사용하는 `store_export` 및 `write_worker_result`를 이용한다. 실제 AirWave HTTPS 로그인·CSS 선택자·다운로드 성공을 확인하는 테스트는 아니다. 기존 별도 Edge 모의 UI 테스트는 유지한다.

## 수용 조건

1. 서버 3대는 실제 OS 프로세스 3개로 겹쳐 실행되고 모두 독립 CSV를 내보낸다.
2. 서버 5대는 동시에 최대 3개 프로세스만 실행하고 처음 세 서버 뒤로 나머지 두 서버가 시작한다. 시작 시각·종료 시각을 측정해 겹침과 제한을 검증한다.
3. 서버 A 실패 시 B/C/D/E 진행, 재시도 중에도 미실행 서버 우선, 수집 결과는 서버별로 격리.
4. Windows 패키징 EXE에서 3·5개의 실제 `--worker` 프로세스를 기동해, 미설정 CSS의 fail-closed(코드 44) 결과와 실행 제한을 확인한다. **실제 CSV 성공을 주장하지 않는다.**
5. 반복 부하 테스트: 전체 배치를 여러 차례 돌리고 CSV 교차 저장/파일 일부 손상/프로세스 누수/프로세스 핸들·메모리 순증가 여부를 점검한다. 테스트 실패 시 보고용 dummy 데이터만 보존한다.
6. PR 기본 CI는 긴 테스트가 개발을 막지 않도록 **짧은 반복 시험(2분)** 실행. 별도 `workflow_dispatch`로 **5·30·120·240분** Windows 장시간 시험 제공. 로컬 Windows는 480분(8시간)도 실행 가능.
7. 모든 Linux/Windows 기존 테스트·Ruff·Windows EXE 빌드와 시작 검증 통과. 실제 사내 AirWave 검증 제외.

## 리스크와 한계

- CI의 모의 워커는 실제 Chrome/Edge 및 AirWave 인증을 수행하지 않으므로 서비스 통합 성공의 증거가 아니다.
- 일반 Windows CI는 2분만 연속 관찰하고 2시간 이상 장시간 시험은 별도 선택 실행 필요하다.
- 장시간 관찰은 테스트 전용 프로세스/파일만 실행하고 운영 파일·계정·예약 작업에는 접근하지 않는다.
- Windows 8시간 연속 환경 검증은 로컬 PC에서만 지원하며 CI에서 이미 수행했다고 주장하지 않는다.
