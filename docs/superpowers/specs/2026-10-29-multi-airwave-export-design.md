# AirWave CSV Exporter 다중 서버 확장 설계 (Superpowers)

- 작성일: 2026-10-29
- 상태: **설계 검토 요청 / 구현 미승인**
- 대상 저장소: sebia1993/aruba-airwave-csv-exporter
- 대상: Windows 11 (64-bit), Aruba AirWave 8.2.14.0
- 사용자 확정: **최대 5대 등록**, **기본 동시 실행 3대**, 나머지는 **대기열 처리**
- 범위: 설계 및 검토. 이 문서만으로 기능 구현, 릴리즈 또는 기존 데이터 변경을 승인한 것은 아님.

## 1. 목적과 성공 조건

현 운영 환경의 AirWave 3대에서 같은 예약 시간에 장비 목록 CSV를 수집하고, 향후 서버를 2대 더 등록하더라도 동일한 Windows 11 EXE 한 개로 운영한다. 각 서버의 로그인, 브라우저, 전체 폴더 확장, CSV 저장·검증은 서로 영향을 주지 않는다.

성공 조건:
1. 최초 설치 시 등록 서버는 0대일 수 있으나, 운영 등록은 1~5대이며 기본 최대 동시 실행은 3개다.
2. 5대가 활성화된 경우 먼저 3대를 실행하고, 슬롯이 비면 4·5번이 자동으로 시작한다.
3. 어떤 서버의 로그인 또는 다운로드가 실패해도 다른 서버의 실행이 중단되지 않는다.
4. AirWave 서버마다 Devices > List / Default View = Devices / Top / 필터 없음 / Expand folders to show all devices / 확장 후 15~30초 확인을 **독립적으로** 적용한다.
5. CSV 파일, 기준 건수, latest.csv, 실행 이력 및 자격 증명이 서버별로 분리된다.
6. 기존 단일 서버 이용자는 업데이트 후 데이터와 설정을 잃지 않고 그대로 동작해야 한다.
7. 예약 작업은 하나이고, 실행 시 활성 서버를 일괄 수집한다. 사용자가 직접 개별 서버도 테스트할 수 있어야 한다.

## 2. 제외할 기능과 절대 피할 결과

- 제외: 여러 CSV를 하나로 병합, AirWave 장비 설정 변경, 사용자 권한 확대, SSO/MFA/CAPTCHA 우회, 외부 서버 업로드, 자동 GitHub 릴리즈, 서버별 서로 다른 예약 시각.
- 피해야 할 결과: A 서버 CSV가 B 서버 파일을 덮어쓰기, 실패한 서버 때문에 전체 수집 중단, 무제한 Edge 브라우저 실행, 유효하지 않은 CSV를 성공으로 표시, 비밀번호/쿠키/내부 장비정보 GitHub 노출.
- 외부 네트워크 연결은 사용자가 지정한 AirWave HTTPS 주소와 Windows 환경이 요구하는 인증 경로에 한정한다.

## 4. 구현 접근법 비교

| 접근법 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| A. 서버별 EXE/예약작업을 5개 등록 | 현재 코드를 거의 그대로 재사용 | 설정·예약·성공확인이 5배, 실행 중복·파일 충돌 가능 | 권장하지 않음 |
| B. EXE 하나 + 스레드 3개 (ThreadPoolExecutor) | 경량이며 단순 | Playwright API는 스레드 안전하지 않아 스레드마다 인스턴스를 새로 열어야 함; 멈춘 스레드 강제 종료 어려움 | 대안 |
| **C. EXE 하나 + 독립 워커 프로세스 최대 3개** | 브라우저/로그인/오류 격리, 서버별 강제 종료 및 재시도 가능 | 추가 메모리·프로세스 관리가 필요 | **추천 설계** |

사용자는 5대 등록·기본 3대 동시 실행·대기열이라는 **운영 방식**을 확정했다. C의 **워커 프로세스 격리 방식**은 이 문서의 기술적 제안으로, 구현 전에 본 설계 문서를 검토·승인받는다.

참고: Playwright Python 공식 문서는 API가 thread-safe가 아니며, 다중 스레드 사용 시 각 스레드에 Playwright 인스턴스가 필요하다고 명시한다. https://playwright.dev/python/docs/library

## 5. 시스템 구성 및 실행 흐름

~~~text
Windows 작업 스케줄러 (매일 HH:MM, 작업 1개)
       |
       v
AirWaveCsvExporter.exe --run-all
       |
       +-- 글로벌 run.lock / 실행 ID 발급 / 활성 서버 목록 스냅샷
       |
       +-- 작업 대기열 (최대 5개, FIFO 기본)
       |     +-- 슬롯 1 --> 워커 프로세스 A --> AirWave A --> A 전용 CSV
       |     +-- 슬롯 2 --> 워커 프로세스 B --> AirWave B --> B 전용 CSV
       |     +-- 슬롯 3 --> 워커 프로세스 C --> AirWave C --> C 전용 CSV
       |     +-- 대기: D / E
       |
       +-- 슬롯이 비면 다음 대기 서버 시작
       +-- 일시적 오류는 서버별 재시도 시각을 예약하고 슬롯 반환
       +-- 실행 결과 집계 및 최종 요약 저장
~~~

- 서버 5개 등록, 활성 서버 3개라면 3개만 병렬 실행하고 대기열은 비어 있다.
- 5개 모두 활성화되면 시작 즉시 최대 3개만 실행한다.
- 서버별 개별 브라우저 세션을 갖고 쿠키, HTML 상태, 다운로드 임시 경로를 공유하지 않는다.
- Python subprocess로 같은 EXE를 내부 워커 옵션으로 실행한다. 부모가 워커 결과를 수집한다. EXE의 일반 GUI 화면과 워커 역할은 분리한다.
- GUI는 tkinter 메인 스레드에서만 갱신한다. 상태 파일/프로세스 메시지를 통해 백그라운드 실행 정보를 읽는다.
- Windows Job Object 기반 워커 프로세스 트리 정리(또는 검증된 동등 기법)를 구현해 타임아웃 시 Edge 자식 프로세스가 남지 않게 한다.
- 전체 배치 잠금은 부모만 획득한다. 자식 워커가 같은 잠금을 다시 잡아서 교착 상태를 만들지 않게 한다.
- 동시 실행 제한은 브라우저 프로세스 수에 적용하고 재시도 대기 중인 서버는 슬롯을 점유하지 않는다.

### 5.1 FIFO와 재시도 공정성 예시

~~~text
09:00:00  A / B / C 시작; D / E 대기
09:00:40  A 일시적 오류 -> 재시도 예정(09:03:40); A 슬롯 반환
09:00:41  D 시작; E 대기
09:01:10  B 성공 -> E 시작
09:03:40  A 재시도 시각 도달 -> 빈 슬롯을 기다렸다 실행
~~~

사용자가 처음 등록한 서버 D/E가 A의 180초 재시도를 기다리느라 불필요하게 지연되지 않도록 **미실행 서버 우선**, 이어서 재시도 예약 작업 순서로 처리한다. 대기열은 Windows 스케줄러의 Queue 옵션이 아니라 **애플리케이션 내부 큐**다.

## 6. 설정/데이터 모델 (v2 제안)

~~~json
{
  "schema_version": 2,
  "schedule_time": "09:00",
  "parallel_limit": 3,
  "export_root": "C:\\AirWaveCSV",
  "servers": [
    {
      "id": "airwave-01",
      "display_name": "AirWave A",
      "server_url": "https://airwave-a.example.invalid",
      "username": "operator",
      "enabled": true,
      "selector_profile": "selectors/airwave-01.json"
    },
    {
      "id": "airwave-02",
      "display_name": "AirWave B",
      "server_url": "https://airwave-b.example.invalid",
      "username": "operator",
      "enabled": true,
      "selector_profile": "selectors/airwave-02.json"
    }
  ]
}
~~~

결정/규칙:
- 등록 서버 수는 **0~5개**(최초 실행 시 0개 허용). 저장 시 6번째 등록은 거부한다. 활성 서버가 0개인 배치는 수집하지 않고 '대상 없음'을 명확히 표시한다.
- 병렬 동작 기본값 **3개**. 설정 범위는 1~5개로 설계하되 4~5개로 늘리면 리소스 경고를 표시한다. 사용자가 설정하지 않으면 3개로 유지한다.
- 서버 ID는 생성 후 변경하지 않으며 다른 서버에 재사용하지 않는다. 최초 기존 서버의 ID는 airwave-01로 이관하고 이후 신규 ID는 영속적인 일련번호를 늘려 부여한다(기존 서버 삭제 후에도 번호 재사용 금지). 동시에 등록한 서버 수의 제한과 ID 일련번호 최대값은 별개다. 표시 이름은 수정 가능하다.
- 서버 URL의 스킴은 HTTPS만 허용하고 정규화한 동일 URL의 중복 등록을 거부한다.
- 등록 서버의 enabled=false는 예약 배치에서 SKIPPED로 기록하고 수집하지 않는다.
- 설정 JSON에 비밀번호/세션/쿠키 저장 금지. 서버별 Windows Credential Manager 저장소 키를 사용한다.
- CSS 선택자는 각 서버별 파일을 우선한다. 검증된 공통 선택자 템플릿의 재사용은 허용하되 실제 UI 검증 없는 자동 적용은 하지 않는다.
- 사용자별 LocalAppData에 설정/선택자/실행 이력을 보관한다. 공개 GitHub 업로드 금지.
- 프로그램 실행 중 설정 변경 시 이미 시작한 배치는 **시작 시점의 설정 스냅샷**을 사용한다. 이를 위해 부모는 실행 당시 서버 프로필·선택자 내용(비밀번호 제외)을 읽고 사용자 접근만 가능한 run_id별 임시 스냅샷을 만들어 각 워커에 참조 경로만 전달한다. 임시파일은 수집 종료 시 정리하고 작업 실패 시에도 비밀정보가 남지 않게 한다. 비밀번호는 워커가 자기 계정의 Windows Credential Manager에서 직접 읽으며 명령행/스냅샷 파일에 넣지 않는다. 새 설정은 다음 배치부터 적용된다.

## 7. 파일 격리·CSV 검증·보존 정책

~~~text
C:\AirWaveCSV\
  airwave-01\
    latest.csv
    AirWave_Devices_20261029_090000.csv
  airwave-02\
    latest.csv
    AirWave_Devices_20261029_090025.csv
  airwave-03\
    latest.csv
    ...
~~~

- 파일 경로 구분은 **불변 서버 ID**를 기준으로 하므로 서버 별칭을 바꾸어도 과거 데이터가 분리되지 않는다.
- 각 서버별 다운로드 임시파일과 latest.csv는 해당 서버 하위 폴더에만 접근한다.
- 같은 날짜·시간의 충돌을 방지하기 위해 실제 파일명은 마이크로초/고유 ID를 포함할 수 있다.
- 기존 CSV 검증을 그대로 적용한다. 비어 있음, HTML 오류 페이지, 헤더 누락, 열 개수 오류, UI 총건수 불일치는 해당 서버 실패로 처리한다.
- 장비 수 급감 경고는 **같은 서버의 이전 latest.csv와만 비교**한다. 기본 경고 임계값은 10% 감소이며, 경고 시 날짜별 파일은 기록하지만 해당 서버의 latest.csv는 보존한다.
- CSV의 실제 열 구성 및 여러 페이지가 Export 한 파일에 모두 포함되는지는 현장 AirWave에서 확인해야 한다. 화면 전체 건수와 CSV 데이터 행 수 일치는 필수 조건이다.
- 서버 한 대가 실패해도 나머지 성공 파일은 정상 보존한다.
- 과거 날짜별 CSV는 기본적으로 자동 삭제하지 않는다. 용량 관리·보존기간 정책은 별도 기능이므로 현재 범위에서 제외한다. 서버 삭제 시에도 해당 서버의 CSV는 자동 삭제하지 않는다.

## 8. 장애·타임아웃·재시도 및 종료 처리

서버별 상태:

~~~text
QUEUED -> RUNNING -> SUCCESS
                 \-> WARNING (장비 수 급감)
                 \-> RETRY_WAIT -> QUEUED -> RUNNING -> SUCCESS/FAILED
                 \-> FAILED
비활성 서버 -> SKIPPED
프로그램 강제 종료 -> INTERRUPTED (다음 시작 시 과거 실행 정리)
~~~

- 기존 다운로드 조건 유지: Default View=Devices, Top, 활성 필터 없음, 확장 완료 표시, 확장 후 최소 15초/최대 30초 확인, 다운로드 직전 상태 재검증.
- 로그인/권한 오류, 미확인 선택자, Default View 전환 불가, 보안 인증 추가 요구는 즉시 실패(자동 반복 로그인 금지).
- 일시 네트워크 오류/CSV 비어 있음/다운로드 실패/30초 로딩 타임아웃은 기본 최대 2회 시도, 시도 사이 180초의 **비점유 대기**를 허용한다.
- 네트워크 장애로 재시도해도 다른 서버의 최초 실행을 지연시키지 않는다.
- 제안값: 서버별 작업 총 예산 12분(재시도 포함), 전체 배치 30분. 초과 시 해당 워커 프로세스 트리를 종료하고 FAILED/INTERRUPTED를 기록한다. 실제 환경에서 조정 가능하도록 상수와 로그를 둔다.
- 창 닫기/PC 종료/예외적 종료에서 미완료 서버를 SUCCESS로 표시하지 않는다.
- 다음 예약 때 과거 미완료 배치를 자동 중복 재생하지 않는다. 새 배치로 활성 서버를 다시 수집한다. 필요하면 GUI에서 재실행한다.
- 시작된 배치 중 GUI의 '전체 실행' 중복 클릭은 차단하고, 이미 실행 중이라는 상태를 보여준다.

## 9. Windows 예약 실행과 자격 증명

- Windows 작업 스케줄러에는 **일일 작업 1개**만 유지한다. 활성 서버가 0개면 해당 실행은 '대상 없음'으로 종료하고 성공 수집으로 기록하지 않는다. 기존 작업명 AirWave CSV Exporter - Daily를 재사용한다.
- Windows 예약의 MultipleInstances=IgnoreNew를 유지해 **두 배치가 동시에 시작되지 않게** 한다. 배치 **내부**의 3개 병렬 워커와는 별개다.
- 기존 --run --headless 진입점은 run-all 동작으로 연결하여 예전 예약 작업도 호환되게 한다. 새 예약은 --run-all --headless를 사용할 수 있다.
- 실행 계정은 기존 Interactive 방식과 동일하다. 로그오프·전원 꺼짐 상태 실행은 보장하지 않는다.
- 서버별 자격 증명을 Windows Credential Manager에 저장한다. 자식 프로세스에 비밀번호를 명령행 인수·환경변수로 전달하지 않는다. 같은 Windows 사용자 컨텍스트에서 키를 읽는다.
- 계정 정보 저장 실패는 해당 서버 등록/수집 실패로 처리하고, 잘못된 계정으로 다른 서버에 재사용하지 않는다.
- 스케줄 설정 및 서버 등록 변경은 사용자의 저장/등록 동작으로만 영구 반영한다.

참고: Windows의 IgnoreNew는 새 예약 인스턴스를 무시하며 Queue는 작업 스케줄러 자체의 차례 대기이다. 여기서는 내부 서버 큐와 혼동하지 않는다.
https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-multipleinstancespolicy-settingstype-element

## 10. 기존 사용자 설정 마이그레이션

기존 프로그램의 config.json에는 서버 1대 정보가 있고, 선택자 파일은 selectors.json 하나다.

1. 시작 시 스키마 버전이 없는 v1 설정을 감지한다.
2. 기존 설정 파일을 변경 전에 사용자 전용 디렉터리에 백업한다.
3. 기존 서버를 불변 ID airwave-01로 등록하고 표시명은 AirWave 1로 부여한다.
4. 기존 selectors.json을 첫 서버 프로필로 **복사**한다(원본 삭제 금지).
5. 기존 URL+사용자 ID 자격 증명을 읽을 수 있으면 새 ID 기반 Credential Manager 키로 이전한다. 읽지 못하면 첫 서버는 자격 증명 재입력 필요로 표시한다.
6. 새 설정을 임시파일에 기록하고 유효성을 확인한 뒤 원자적으로 교체한다. 실패하면 이전 설정을 사용하고 안내한다.
7. 기존 최상위 CSV와 latest.csv를 삭제/덮어쓰지 않는다. 최초 마이그레이션 시 원본 백업 위치를 UI에 안내한다. 과거 파일의 자동 이동은 하지 않는다.
8. 서버가 1대일 때 CSV 수집 절차는 기존과 동일하게 유지한다. 변경된 경로는 미리 GUI에 안내한다.
9. 실제 AirWave CSS 선택자가 기존에도 미확인 상태였다면 자동으로 '검증 완료'라고 간주하지 않는다.

이전 상태로 되돌리는 방법은 README에 명시한다. 마이그레이션 반복 시 새로운 서버를 중복 생성하지 않는다.

## 12. 실행 이력과 결과 집계

- 배치 시작 시 run_id를 UUID 기반으로 생성한다.
- 서버마다 server_id, run_id, 단계, 시도 횟수, 시작/종료 시각, CSV 행 수, 결과 코드, 저장 파일의 상대 경로를 구조화 기록한다.
- 배치 요약: 활성 개수/성공/경고/실패/중단/제외/총 소요시간과 서버별 결과.
- 로그는 사용자 PC에만 저장한다. URL, 계정 비밀번호, 쿠키, 세션, 장비 행 데이터는 로그에서 제외한다.
- 결과 종료코드는 배치 기준 **0=전부 정상**, **2=부분 실패 또는 경고**, **1=전체 실패**, **3=실행 대상 없음/전체 설정 유효성 오류**로 제안한다. 서버별 내부 오류 코드는 기존 31/44/45/47/48 등을 유지하여 로그에서 구분한다. 이 분류는 Windows 예약 실행 이력에도 반영된다.
- 프로그램 강제 종료로 최종 요약이 누락되면 다음 실행 시 마지막 상태를 INTERRUPTED로 보정하고 정상 완료로 해석하지 않는다.

## 14. 보안·운영 위험과 완화

1. **서버별 로그인 격리:** 서로 다른 브라우저 프로세스와 계정 키, 쿠키 공유 금지.
2. **브라우저 비용:** 기본 최대 3개로 제약. Windows에서 실제 RAM/CPU 계측 후 운영 값 조정.
3. **CSS 불일치:** AirWave 8.2.14.0 현장 DOM 미확인 경우 서버별 안전 실패; 추정한 CSS를 일괄 적용하지 않음.
4. **서버 다운/성능 저하:** 해당 서버만 실패/재시도; 나머지 대기열 처리 지속.
5. **CSV 손상·교차 덮어쓰기:** 서버 ID 기반 저장 경로, 최신본 원자적 갱신, 총건수 비교.
6. **프로세스 고착:** 서버별 타임아웃과 프로세스 트리 종료, 부모 배치 제한 30분.
7. **버전 마이그레이션:** 기존 로컬 설정·자격 증명/CSV를 보존하고 단계별 롤백 가능.
8. **공개 GitHub:** 실서버 URL, IP/MAC, 장비 목록 CSV, 계정/비밀번호/쿠키/회사 정보 공개 금지.
9. **예약 중복:** Task Scheduler IgnoreNew와 어플리케이션 글로벌 단일 배치 잠금 유지.

**빌더 체크 결론:** 구현 계획을 막는 필수 미정 정보는 찾지 못했다. 다만 독립 워커 프로세스 방식, 배치 제한 및 나머지 설계 기본값은 구현 전에 사용자 설계 승인 대상이다. 사내 AirWave 실제 DOM·인증 방식은 현장 검증 전제로 유지한다.

**다음 단계 게이트:** 이 설계 문서가 승인되기 전까지 새로운 제품 코드, EXE, 릴리즈, main 반영을 진행하지 않는다. 승인 후 Superpowers writing-plans 절차로 작업 단위를 세분화한다.
